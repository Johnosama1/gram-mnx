# إصلاح Telegram Authentication والـ APIs وقاعدة البيانات

## الهدف
إعادة بناء مسار تسجيل الدخول والبيانات بحيث يبدأ التطبيق من Telegram WebApp الموثّق، وينشئ جلسة خادمية آمنة، ثم تعتمد كل صفحات المستخدم على هذه الجلسة وعلى قاعدة البيانات الحقيقية فقط، مع إصلاح Mine وCombo وباقي المسارات واختبار النسخة المنشورة.

## التنفيذ

### 1. تهيئة Telegram مبكرًا وموحّدة
- إنشاء طبقة bootstrap واحدة تنتظر Telegram WebApp، تستدعي `ready()` و`expand()`، وتقرأ `initData` و`initDataUnsafe` قبل تركيب مزوّدي البيانات أو بدء أي طلب مستخدم.
- اعتبار `initDataUnsafe` مصدرًا للعرض الأولي فقط، وعدم استخدامه كهوية موثوقة أو صلاحية Admin.
- إزالة الاعتماد الأمني على localStorage والـ IDs المكتوبة داخل الكود؛ يبقى التخزين المحلي للعرض المؤقت فقط ولا يسمح بفتح التطبيق قبل نجاح التحقق الخادمي.
- عرض حالة Preview/خارج Telegram بوضوح من دون إنشاء هوية وهمية أو إرسال طلبات مستخدم فاشلة.

### 2. جلسة خادمية موثوقة
- إصلاح endpoint تسجيل Telegram ليتحقق من توقيع `initData` بواسطة Bot Token، ويتحقق من عمر البيانات، وينشئ المستخدم بشكل ذري عند أول دخول.
- بعد التحقق، إصدار session cookie موقّعة وآمنة وHttpOnly مرتبطة بـ Telegram ID؛ باقي الـ APIs تستخرج المستخدم من الجلسة بدل إعادة الثقة في ID أو إعادة تمرير initData لكل عملية.
- إبقاء إعادة المصادقة بالـ initData كمسار bootstrap/تجديد فقط، مع فصل واضح بين 401 و403.
- حماية Admin بعضوية Admin الخادمية بالإضافة إلى جلسة كلمة السر الحالية، بلا صلاحيات مشتقة من الواجهة.

### 3. توحيد طبقة API والأخطاء
- استبدال patch العام لـ `fetch` بعميل API صريح ينتظر اكتمال bootstrap، يرسل cookies، ويحوّل 401/403/404/500 إلى أخطاء مصنفة.
- منع prefetch وأي provider من طلب بيانات المستخدم قبل نجاح المصادقة.
- تسجيل تفاصيل أخطاء قاعدة البيانات والخادم في server logs مع إرجاع رسالة آمنة ومحددة للواجهة.
- إزالة fallback/mock الذي يغيّر أرصدة أو يخفي فشل الشبكة، مع إبقاء آخر لقطة للعرض فقط إذا كانت موسومة بأنها غير موثقة وغير قابلة للإنفاق.

### 4. إصلاح قاعدة البيانات والعمليات الذرية
- فرض uniqueness على `gm_users.telegram_id` وعلى محاولة Combo اليومية، وروابط الإنجازات/الدعوات اللازمة لمنع التكرار.
- تحويل إنشاء/تحديث مستخدم Telegram إلى upsert ذري مع فحص أخطاء قاعدة البيانات بدل تجاهلها.
- إنشاء RPC ذرية لمحاولة Combo: قفل محاولة اليوم، التحقق من الاختيارات المخزنة، تسجيل النتيجة، وإضافة المكافأة مرة واحدة في transaction واحدة.
- مراجعة Daily Check-in والمهام والإحالات والهدايا لتكون عمليات التسجيل والمكافأة idempotent وذرية، ومعالجة أخطاء القيود صراحة.
- الحفاظ على deny-by-default للجداول واستخدام الخادم الموثوق فقط للوصول إليها.

### 5. إصلاح Mine وCombo وباقي الصفحات
- Mine: تحميل Holding و24H Earned وTotal Earned وحالة التعدين والمعدل من endpoint واحد خادمي موثوق، وتنفيذ Claim عبر RPC الحالية بعد تدقيقها ضد التكرار؛ لا حسابات مالية معتمدة على الواجهة.
- Combo: تحميل حالة اليوم للمستخدم الموثق، اختيار 3 عناصر، إرسالها للخادم، التحقق من combo الحقيقي، منع المحاولة الثانية، وتحديث MNX فقط عند النجاح.
- Tasks وDaily Check-in وFriends وProfile وGift: تمريرها إلى عميل الجلسة الموحد، إزالة الطلبات الصامتة، وإظهار حالات الخطأ المناسبة.
- Admin: إبقاء كلمة السر والجلسة الإدارية مع حماية كل endpoint خادميًا.

### 6. التحقق والإطلاق
- التحقق من وجود Bot Token وربط قاعدة البيانات في بيئة الخادم من دون كشف القيم، ومراجعة عدم وجود localhost أو أسرار في الواجهة.
- اختبار قاعدة البيانات والـ APIs لحالات: بدون Telegram، initData غير صالح، جلسة صحيحة، محاولة مكررة، وصلاحيات Admin.
- اختبار واجهة الإنتاج بتدفق Telegram موقع فعليًا: إنشاء المستخدم، Mine، Tasks، Check-in، Combo وCheck Combo، Claim، Friends، Profile، وGift.
- نشر الإصلاحات ثم إعادة تنفيذ اختبارات الـ APIs والواجهة على النسخة المنشورة نفسها وتوثيق أي قيد لا يمكن اختباره خارج عميل Telegram.

## تفاصيل تقنية
- session cookie موقّعة بمفتاح مستقل من البيئة وليست مبنية على User ID أو localStorage.
- كل mutation مالية أو مكافأة تكون transaction/RPC ذرية داخل قاعدة البيانات.
- نفس الأصل والـ HTTPS هما المسار الافتراضي في الإنتاج؛ لا CORS إضافي ما لم يوجد backend على origin مختلف فعليًا.
- لا mock authentication ولا بيانات تجريبية في production.
